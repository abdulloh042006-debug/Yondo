## 0. Top findings
1. The gifts API is a **stub**: `/vendor/orders` and `/vendor/earnings` always answer 503, `POST /gifts/checkout` is 503, real vendor orders/payouts do not exist. Only product CRUD-lite and the manual **test-order** flow (`/gifts/test-orders`, `is_test_order`, `real_money_moved:false`) work. There is no vendor profile, vendor approval, product images or product delete.
2. Money has no read side: no fee quote (the fee is computed only when `POST /payments/bookings/{id}` creates the Payment), no payouts/earnings API (model `CompanionPayout` held/ready/paid exists, payout = `subtotal`), no refund entity (only `Payment.refund_required`), no cancellation/abuse stats. The current code adds the fee **on top of the customer total** (`amount = subtotal + fee`), which matches TZ §26. `platform_fee_bps` is env only, with no audit trail.
3. The default theme is **Gul**, not Yondo (`ui/theme.tsx` `saved()` falls back to `'gul'`). The `yondo-tun` axe flake is a transition-timing artefact (A.5), not a palette bug.
4. The creator of an SOS alert cannot read its status (`POST /safety/bookings/{id}/sos` only; `acknowledged` is visible to admins only). "Awaiting review / Reviewed" needs a new endpoint plus an owner-supplied monitoring-hours value.
5. The live map (future) contradicts the S25 rule "location is never sent to the Yondo server" → needs an owner decision plus a privacy-policy change before any build.
6. Conflicts to flag: TZ §42 (auth = phone+OTP, Google/Apple later) vs the owner's Google+Telegram login; the TZ §31 gift statuses differ from the API enum; the nav uses a **heart** icon (`Layout.tsx` ICONS.heart, `HeartButton`), which the "no hearts" rule should cover.

## A. Theme system audit
1. **Where**: tokens in `apps/web/src/styles.css` — `:root,[data-theme='gul']` (l.5), `rausch` (l.20, label "Jurnal"), `stone` (l.34), `yondo`/`yondo-tun` (l.1220-1252) plus ~20 override rules `[data-theme^='yondo'] …` (l.1255-1312: danger, invalid input, tags, banner, toast, aurora glow, glass, media). Registry/picker/persistence: `ui/theme.tsx` (THEMES array → `ThemePicker`, rendered only in `pages/Settings.tsx`). `design-prototype/design-system/tokens.{css,json}` is a separate system (prefers-color-scheme, success/error/warning hues); apps/web does not use it.
2. **Switching/persistence**: click → `document.documentElement.dataset.theme` + `localStorage['yondo.theme']`; `applySavedTheme()` in `main.tsx` before React renders; device-local (not synced to the account, unlike `ui_locale`); unknown/missing → `gul`. `<meta name="theme-color">` is static `#f3ebdf` and is never updated on switch (wrong browser chrome colour in `yondo-tun`).
3. **Token contract (12 required)**: `--c-bg --c-fg --c-muted --c-surface --c-primary --c-on-primary --c-line --c-chip --c-scrim --c-on-media --f-display --f-sans`. Optional: `--c-glow`, `--ok/--warn/--bad` (root defaults #1a6b43/#7a4b00/#a3231b; Yondo sets them to `--c-fg`), `color-scheme` (night themes MUST set `dark`; `:root` is light). Derived (never set per theme): `--muted-ink`, glass, borders, hover via `color-mix`.
4. **Rules**: Yondo themes = ink #111111 / paper #F5F2EC (+ white) / carrot #E8501A only; greys only as ink/paper mixes; carrot never small text (3.36:1 on paper) → fills with ink text, borders, glow, dots; status = words + carrot border; glow = carrot at low opacity. FLAG: `#e8501a` is hard-coded 8 times in `styles.css` (override rules), the `.btn.danger{color:#fff}` base and the swatches in `theme.tsx`; a new theme must not copy them.
5. **axe flake `yondo-tun` /login (root cause, evidence-based)**: the numbers in the log match **stale Gul values on transitioned properties**. 2.39 = #111111 (yondo-tun `--c-on-primary`, already flipped) on #8e3140 (Gul `--c-primary`, bg not yet transitioned: `.btn{transition: background .2s}`); 1.12 = #241c16 (Gul `--c-fg`) on ink for `.lang-opt` (`transition: background/color .2s`, ru/en buttons). The sweep flips `dataset.theme` after `goto`, waits 1.7 s, and the browser clock did not advance the transitions (throttled/unpainted page after ~10 contexts). Only a **dark** target turns stale light foregrounds into failures — hence only `yondo-tun`. It passed on the rerun → timing flake. Fix (test side, deterministic): before each scan `await pg.emulateMedia({ reducedMotion: 'reduce' })` (CSS l.1028 forces `transition-duration:.001ms`) or `waitForFunction(() => document.getAnimations().length === 0)`. Product side (optional, 3 lines): `setTheme` adds `data-theme-switching` for one frame with `*{transition:none!important}`.
6. **How to add a theme**: (1) append `{id,label,hint,swatch}` to THEMES; (2) add `[data-theme='id']{12 tokens + color-scheme}` after the stone block, using only `var()`/`color-mix` for derived values; (3) if a status/glow override is needed, copy the `[data-theme^='yondo']` pattern, never new literals; (4) i18n `theme.<id>.label/hint` in uz/ru/en (parity test enforces it); (5) update `<meta theme-color>` via a `THEMES[].chrome` field + `setTheme`; (6) contrast-check: fg/bg ≥ 4.5, muted ≥ 4.5, primary/on-primary ≥ 4.5, 3:1 for borders and focus ring; (7) extend tests: e2e theme list (`e2e/run.mjs` theme sweep ~l.850, 5 themes × 15 pages axe) and add a unit test that every THEMES id has a CSS block with all 12 tokens (parse `styles.css`); (8) screenshot at 360/1440. Yondo-family themes need an owner rule check first (CLAUDE.md §7).
